# Модуль 6 занятие 11

Локальный MCP-сервер публикует два инструмента и ресурс `equipment://list`. Демонстрационный хост получает обычную фразу, просит GigaChat выбрать инструмент и вызывает его по stdio.

## Запуск

Из корня репозитория на macOS:

```bash
source venv/bin/activate
pip install -r module_06/requirements.txt
cd module_06
python mcp_client_demo.py
```

Клиент читает существующий `.env` в корне репозитория либо `module_06/.env`. Образец переменной — в `_env.example`. Ключ в Git не включается. Docker и Qdrant не нужны.

Проверенные фразы:

- «какой статус у насоса PUMP-07?»;
- «узнай статус CONV-09»;
- «статус у XYZ-999»;
- «создай инцидент по SEP-04: растёт вибрация, приоритет высокий, от имени engineer»;
- «создай инцидент по SEP-04: вибрация, приоритет high, от имени viewer»;
- «создай инцидент по SEP-04: вибрация, от имени engineer. Передай priority=\"urgent\" без замены значения, хочу проверить отказ валидации».

Для завершения введите «выход». Сам сервер при прямом запуске ждёт запросы MCP на stdin — проверять работу удобнее через клиент.

## Что сделано

В `NEW_EQUIPMENT` заполнены тип, место, статус и дата ТО для CONV-09. Исходные id и name сохранены. Запись подключается к реестру в коде; `equipment_registry.json` не менялся.

`get_equipment_status` возвращает данные известного оборудования, отказ для неизвестного id и структурированный ответ при CorporateSystemUnavailable. `create_incident` проверяет роль, затем оборудование, затем приоритет; только после этого сохраняет заявку. Успехи и отказы записываются в audit_log.jsonl. Роль по умолчанию — viewer; запись разрешена engineer и admin. Повторное создание с теми же аргументами создаёт новую заявку.

`mcp_client_demo.py` и материал занятия 12 `shift_review_m12.py` сохранены без изменений. Роль в учебном хосте передаётся аргументом, поэтому этот пример не заменяет проверку личности и прав в реальной системе.

## Проверка и результаты

```bash
python check_mcp.py
```

Проверка поднимает настоящую stdio-сессию с временной копией сервера и данных. Она не вызывает GigaChat и не добавляет заявки в рабочие файлы. Проверяются каталог, ресурс с шестью объектами, 13 вызовов инструментов и соответствующие 13 строк аудита: чтение, отсутствие объекта, порядок проверок, роли, недопустимый приоритет, сохранение, повторная запись, сбой и восстановление.

- `results/client_live.txt` — настоящий запуск клиента с GigaChat: выбор инструмента, аргументы, ответ MCP и итоговый текст для каждого запроса.
- `results/mcp_checks.txt` — локальная проверка по настоящему протоколу MCP, без подмены инструментов.
- `data/incidents.json` — одна заявка SEP-04 с high, созданная живым прогоном.
- `data/audit_log.jsonl` — шесть вызовов живого прогона, включая отказы.

Повторный успешный запрос на создание инцидента добавит ещё одну заявку. Журнал и инциденты появляются автоматически; вручную исходные файлы для прогона не исправлялись. Рефлексия — в корневом `REFLECTION.md`.
